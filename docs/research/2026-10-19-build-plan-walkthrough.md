## 从真实状态得到的设计结论

| 状态位置 | 可采取的动作 | 相比合理规则基线的增量 |
| --- | --- | --- |
| cJSON 配置成功 | 执行已有编译命令 | 本轮没有增量证据 |
| zstd 文档说明直接 Make 构建 | 不创建独立 configure 步骤 | 构建系统适配规则即可做到；不当作模型优势 |
| libusb 缺少 libudev，CI 已提供包名 | 执行有来源的安装候选并复查 | 带同样候选的规则即可做到；不能称未知依赖自动诊断 |
| libusb 编译成功、测试未执行 | 执行既定验证，不直接交付 | 验收状态必须与编译状态分开；规则也能做到 |
| libusb `stress_mt` 失败 | 保留失败证据，生成调查交接请求 | “验证失败接管”规则同样可以；尚无实际 Agent 恢复数据 |

由此支持初始方案 + Workflow 的工程可执行性，以及将“已有有据候选”和“需要调查”分开的接口设计。本轮没有观察到超出合理规则的选择需求，不据此宣称复杂选择器有效；三个正常/基础异常开发案例也不足以否定整条状态感知研究主线。

目前没有验证：独立 Planner Agent 的方案质量、未知依赖的调查、Agent 返回后的控制权回收、方案修订和状态失效、同状态不同动作的效果、端到端费用收益与干净重建。这些应由后续原型和比较分别回答，不补算成本节省。

## 最小原型应承担的职责

1. 接收项目级初始方案。每步包含阶段、具体命令、执行目录、前提、预期、出处；不要求预知未知错误的修复方法。宏观配置阶段允许包含 bootstrap 和 configure 两个独立步骤。
2. 采集权威事实。记录源码/镜像身份、方案版本、命令 ID、角色、退出码、超时、完整日志及有限预览、产物与测试结果；事实、诊断假设和未知项分开。失败时按构建工具指针收集内部诊断日志。
3. 先实现可解释规则基线：满足前提则执行已有步骤；已有条件修复有明确证据则执行并重查；无候选、失败原因不明或无变化的重复失败则产生 Agent 交接请求。
4. Agent 返回时提交实际操作、日志与方案增量；Workflow 重新检查状态，不凭自然语言总结推进或宣布完成。新依赖或配置变更可能使配置/编译/验证结果失效，初版用显式规则管理。
5. 验收要求属于任务约定，不能由方案生成或修复过程随意降低。`make check`/CTest 退出 0 之外，还需确认实际执行了什么测试。

这些是后续实现规格，不表示本轮已经实现完整运行时。Agent 交接、方案修订、失效重算、独立重建尚需单独验证。

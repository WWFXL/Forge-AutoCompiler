# 恢复 Harness 优化器的当前系统实现上下文

本说明对应 PR #722 合并版本 `64978dd68b86398aa2daa1a44a8755f6b26338a9` 的科研入口，供一次独立离线复分析使用。它是人工整理的实现说明，不是构建轨迹或效果样本。随请求同时提供自动提取的源码片段、行号、完整文件哈希和实际接口 Schema；如说明与源码不一致，应指出冲突，以源码为准。片段不等于整个仓库，缺少的实现不能自行假定存在。

## 当前运行路径与权限

研究入口是 `scripts/forge_simple_system.py:run_simple_system`，采用 `SimpleBuildWorkflow`。初始规划使用 H0；恢复使用同一个 `propose_simple` 函数，仅在真实交接时追加恢复 Harness 指导。在线模型固定 Flash，高级模型仅离线分析材料，没有执行、联网或读取额外源码的工具。

规划和恢复 Agent 均由 LangChain `create_agent` 建立。它们只具有 `list_source`、`read_source`、`read_failure_log` 三个只读工具和 `SimpleBuildActions` 结构化输出接口。没有 Bash、执行候选方案、网络搜索或修改源码工具。输出方案经校验后由 Workflow 执行，得到新失败后才会再次创建恢复任务；不能在同一次恢复对话里先试命令再声称成功。

产品 Lead/compiler、强工具 Agent，以及另行研究过的局部工具恢复，都是其他入口，不是本次恢复 Agent 的权限。经验库是可选配置；本次恢复指导比较不额外引入经验检索。规则路由在外层先于 Agent；离线指导只能影响确实交给 Agent 的任务。

## 输入、输出与反馈

恢复输入包括不可变公开任务、当前完整方案、匹配方案哈希与 handoff_id 的实际交接、初始源码材料、剩余资源及读取进展。交接包含当前失败步骤/原因、最近命令及日志尾部、配置观察、主要产物观察和已成功依赖。源码/日志只是数据，不得覆盖系统权限。独立参考的成功命令、精确评价答案、个人知识库和隐藏推理不提供给在线 Agent。

返回 `SimpleBuildActions`：reason、steps，以及可选 build_directory、discard_dependencies。每步有 step_id、role、command、workdir、requires、source、expected。阶段只允许有序的 dependency/configure/build，ID唯一，前提引用更早步骤，最后 step_id=build。expected 仅说明目的，不是日志成功断言；不能把测试、暂存、交付要求塞进该输出。显式 build_directory 只辅助观察，不能改变实际执行目录。

每次 `propose_simple` 中，结构错误、修订执行约束错误各最多提供一次明确纠正，保留已有工具对话，所有请求计费。格式接受不表示命令已执行。没有“阻塞终态”的专用输出工具；模型可以解释阻塞，但无合法方案时入口按错误/预算结束，不能假定它能通过新工具结束整个系统。服务异常不自动重试。

## Workflow 如何执行和判定

每条命令进入独立严格 Shell；上一条 cd 不延续，应使用 workdir。执行前保护原源码/测试，并做阶段约束检查：禁止关闭严格 Shell、访问 /repro、任意 rm/unlink/rmdir 或混合多逻辑阶段。允许规则明确覆盖的作者 make clean/distclean 前置。目录限仓库或交付目录内；这里不授予仓库外临时目录权限。依赖安装可拆成多个 dependency 步骤；复杂外部依赖构建仍必须符合实际阶段识别和目录接口，不能假定写上 dependency 就会放行。

实际非零、超时或策略拒绝停止后续步骤并交接；策略拒绝会保存126/policy_rejected记录，没有运行对应Shell。命令成功后观察构建系统文件：未知 unknown 可继续已有、有界的方案，不冒充 passed；配置阶段末或构建后出现已知矛盾才交接 configuration_inconsistent。构建命令成功后仍由独立主要组件/真实产物检查确认 primary_completed，不是只看退出0。

## 修订如何影响进度和重建配方

修订须保持任务身份、递增版本、匹配活动交接。普通执行修订必须改变实际命令或 workdir；改说明、改步骤别名不能重新执行同一失败。仅当原命令成功且交接来自配置观察冲突时，允许只改 build_directory，实际核验通过后继续原成功进度，不重跑命令。

系统自动保留未显式废弃的已成功 dependency；遗漏不等于删除。重新列出时须沿用原 ID 和动作；隐式覆盖或改名重复会被拒。确需替换/废弃须在 discard_dependencies 中填旧 ID 与理由。恢复模型不必为了“完整方案”机械复制或改写成功安装步骤。基础镜像已有的依赖与本轮临时安装的依赖不同，后者仍要保留在干净重建配方中。

依赖或配置动作变化时，系统插入生成物清理步骤并失效相关配置/构建后缀；未变的成功前缀及仍有效成功依赖复用原记录。只改构建时按共同前缀保留算法恢复进度。最终配方选择最终有效方案的成功记录，失败、诊断、过时命令不进入。不能承诺系统能推断所有安装命令的语义等价或需要关系。

## 验证、上下文与共同修复

main-build-v1 使用简洁的作者普通主构建目标，不要求单独完整作者测试；默认构建本身包含的目标仍应保留。交付、作者依据的轻量运行、SONAME文件、实际干净重建由独立层执行；Agent不能改参考或降低验收。实际交付运行非零可再次交接，退出0但独立输出断言不符不能靠改裁判解决。新 successful-rebuild-v1 不要求跨重建字节相同，仍要求固定源码/镜像、有效产物、相同轻量命令成功及清理。

线上请求有49000字节消息上限；先移出可补读的初始正文，再缩短交接预览、淘汰旧完整组，必要时把过大的最新AI/Tool组保存原件并生成有界实际片段。不是额外模型摘要。无新证据连续两轮提醒，三轮只保留结构化交付接口；变化后的日志或必要缺失区间仍可补读，不能一概禁止重复读取。

原生轻量验证、作者生成文档例外、SONAME交付、成功依赖保留、修订反馈、上下文压缩、国内HTTPS APT镜像和成功重建标准都已经是共同底座。E53轨迹来自修复前，尚无修复后新的Agent恢复轨迹。不能把旧问题一律当成仍未修复，也不能从代码存在推断其消除了全部问题。不能把这些共同人工机制包装成新 Harness 的收益。

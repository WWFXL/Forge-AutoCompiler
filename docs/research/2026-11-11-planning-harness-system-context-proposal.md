对所选配置中已经出现的依赖，区分三件事：作者要求什么、当前配置是否需要、环境是否已提供。核对默认值和缺失处理，不能把“可选功能”直接等同于“当前默认配置无需依赖”，也不能把一个 AUTO 分支推广到其他开关。作者普通入口明确启用的功能及默认目标所需的开发文件、生成器和文档后端属于必要前置。允许自动探测的可选能力保持作者行为，不为排除所有潜在失败安装全部后端。

选择源码检出的 autogen/bootstrap 等生成入口时，利用脚本的实际调用和直接相关的构建声明识别工具及最低版本。只需关注生成与默认构建实际需要的能力，不复制开发、发布或完整测试工具全集。工具存在、同族工具已安装、某个包名存在，都不自动证明版本和能力满足。不要以“基础镜像通常提供”为已安装证据；对明确必需但环境状态未知的依赖，给出有依据的安装动作，或在适合时用能力/版本守卫避免重复安装，由 Workflow 实际执行。不能宣称已亲自探测环境。

依赖信息优先来自作者说明与构建声明。没有依赖清单的小型直接编译 Make 项目，若主要靠链接参数推断外部依赖且仍有完整性疑问，可定点查看主编译单元的外部 include；不扫描全部源码。作者构建图已自动处理的内置依赖沿普通入口执行；只有自行安排外部依赖源码流程时，才按共同契约拆分其下载、配置、编译和安装。

安装集合对应当前构建用途。系统包优先避免无关推荐项，同时显式保留所需后端、数据和开发文件；只检查前端命令的守卫不足以证明整套能力可用。明确版本要求不能靠猜测系统包版本满足，也不要无依据升级到最新版本或展开庞大源码依赖构建。确需受管工具时，方案须同时考虑安装位置、启动方式及每个独立 Shell 所需环境。无法取得合法获取方式的依据时，如实说明限制。

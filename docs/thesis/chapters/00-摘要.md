# 面向C/C++仓库自动化构建的状态感知动作选择与验证方法研究

> 阅读说明：本稿按版本区分基础系统、恢复接口与经验方法；正向、负向和未观察结果均保留。新增组件不回写旧实验条件。

## 摘要（阶段稿）

C/C++开源仓库的自动化构建涉及依赖准备、配置生成、编译、测试及产物交付。项目之间的构建系统、配置选项和产物组织存在差异，固定指令难以覆盖完整任务；完全依赖大模型逐步操作，又可能增加正常构建中的交互与重复探索。此外，命令退出成功并不等于任务目标、原测试和交付要求全部满足。针对这些问题，本文研究面向C/C++仓库自动化构建的状态感知动作选择与验证方法。

基础方法由模型依据仓库证据生成阶段方案，Workflow维护步骤依赖、执行记录与当前目标。系统依据真实配置和命令反馈选择继续执行、受限直接修订或Agent恢复：具有作者声明及实际配置证据的特定BOOL偏差可以直接处理，复杂异常则由Agent返回修订方案。方案改变后，从首个变化位置重新执行受影响后缀，并通过源码保持、原测试、精确交付及同镜像干净重放判断完整完成。在此基础上，本文设计两层经验使用方式：同项目的已验证阶段方案在匹配源码、镜像及任务条件后省去重复规划；未命中时，按当前目标、阶段及真实失败检索跨项目条件经验，辅助规划与恢复。每次Agent任务固定一次选择，成功方案及失败轨迹分别保存，后续可用范围由实际验证证据限定。

实验按版本分别评价完整系统、状态组件、恢复接口及经验增量。八个已见任务、两次重复的系统比较中，Forge与强工具Agent均完成16次任务，Forge模型估费低22.9%，累计耗时接近。固定方案30次组件实验中，四次有依据的直接配置修订均完整完成且无需新增恢复模型请求。同项目方案复用24次比较中，两方法均10/12完整；复用在线估费低73.4%、请求由58降至11，累计时间接近。原条件下6次复用全部零模型调用且完整通过；目标改为Debug后仍需恢复，四个simdutf槽因完整测试预算耗尽而未完成，未观察层不填通过或失败。

同一24条经验库下的36次检索比较中，无经验、原来源检索和状态目标检索分别11/12、10/12、11/12完整。状态目标检索相对原来源在线估费低3.9%、多完成一次，累计时间高22.9%；相对无经验在线费低6.3%、时间高5.8%，计入一次既有制库费后仍更贵，体现在线节约与部署成本的取舍。

结果支持基础状态方法与固定条件下方案复用的实用价值，也表明经验的检索、实际采用、正确动作实例化及成本收益需要分别评价。结论限于所测任务、对应版本及已披露的样本暴露，不证明任意仓库总体最优或普遍持续改进。

## Abstract (Working Draft)

Automated building of C/C++ repositories involves dependency preparation, configuration, compilation, testing, and artifact delivery. Differences in build systems, configuration options, and artifact layouts limit fixed command templates. Delegating every step to a language model may add interaction and repeated exploration, while a successful command alone does not establish that the complete task has been satisfied.

This thesis investigates state-aware action selection and verification for repository-level building. A model generates a stage-based plan from repository evidence, and a workflow maintains dependencies, command records, and task goals. Observed configuration and execution feedback determine whether to continue, apply a bounded direct revision, or request an agent-generated repair. Direct revision is limited to supported Boolean deviations with author declarations and actual configuration evidence. After revision, execution resumes from the first changed step. Source preservation, original tests, exact delivery, and clean replay under the same image determine completion. A two-level experience design separates executable plans for previously built projects from conditional cross-project guidance. Matching project plans can skip repeated initial planning; otherwise, current goals, stages, and observed failures guide retrieval for planning or recovery. Experience is selected once per agent task, and the scope of a saved plan is bounded by its actual validation evidence.

Experiments evaluate the base system, state components, recovery interfaces, and experience under separate versioned conditions. On eight previously examined tasks with two repetitions, both Forge and a strong tool agent completed 16 tasks. Forge used 22.9% less estimated model cost with similar cumulative runtime. In a 30-run fixed-plan experiment, all four evidence-backed direct configuration revisions completed without additional recovery requests. A separate 24-run project-plan reuse comparison completed 10/12 runs in each treatment. Reuse reduced online model cost by 73.4% and requests from 58 to 11, with similar cumulative runtime. All six runs with unchanged task conditions completed without model calls. Changed Debug goals required recovery, and four simdutf runs exhausted their full-test execution budget; later validation layers remained unobserved.

In a separate 36-run comparison using the same 24-entry experience bank, no experience, source-based retrieval, and state-and-goal retrieval completed 11/12, 10/12, and 11/12 runs, respectively. State-and-goal retrieval reduced online estimated cost by 3.9% relative to source-based retrieval and completed one more run, while cumulative runtime increased by 22.9%. Relative to no experience, online cost fell by 6.3% and runtime rose by 5.8%; including one historical bank-creation cost made deployment more expensive for this workload.

The results support the practical value of the base state-aware method and plan reuse under fixed conditions. They also distinguish experience retrieval, adoption, correct action instantiation, and economic benefit. Claims remain limited to the evaluated tasks, versions, and disclosed development exposure rather than arbitrary-repository optimality or general continual improvement.

**Keywords:** automated building; C/C++ repositories; state awareness; action selection; agent harness; experience reuse; reproducible verification

# 面向C/C++仓库自动化构建的状态感知动作选择与验证方法研究

> 版本说明：本稿补入E51首轮离线Harness提案与24次固定比较，保留其完成与成本的混合结果；既有实验均按各自版本和分母使用。

## 摘要（阶段稿）

C/C++开源仓库的自动化构建涉及依赖准备、配置生成、编译及产物确认。构建系统、配置选项和依赖组织的项目差异，使固定指令难以覆盖真实仓库；完全交由大模型逐步操作，又可能增加正常路径的交互与重复探索。同时，命令成功不等于有效主产物、原测试和可复现交付全部满足。本文研究如何在固定构建模型条件下，结合当前执行状态和经过验证的历史经验，选择合适动作并确认实际任务完成。

本文构建模型规划、Workflow执行与失败恢复相结合的方法。规划Agent根据作者材料生成依赖、配置和构建动作，Workflow保存阶段目的、命令记录及有效进展；系统综合退出码、日志、实际配置与主要产物，选择继续、受限直接动作或Agent修订。修订后从首个变化位置重执行受影响后缀。验证按任务版本区分主要产物、适用作者测试、源码保持、精确交付与同镜像干净重放。进一步设计两层经验使用方式：相同源码、镜像和任务身份的已验证阶段方案直接执行，省去重复规划；无精确方案时，检索带适用条件和证据的跨项目建议，作为规划或新恢复任务的一次固定上下文。保存成功方案与失败轨迹，但不把检索命中等同于正确采用或持续改进。

实验分别评价系统效果、状态组件、恢复接口和经验增量。九个开发暴露项目、三种构建系统、两次重复的54次主构建比较中，基础Forge、经验Forge与强工具Agent分别完成18/18、18/18、17/18。基础在线模型估费比强工具低60.5%，累计时间高42.2%；经验比基础在线费低52.5%、累计时间低52.2%，但96.3%的时间差集中于double-conversion，不能视为稳定加速幅度。精确方案层六次复用均零模型且实际重建、交付与重放通过，时间比基础低12.1%。计入一次既有方案获取和经验库提炼后，本批经验总模型成本仍高于基础在线成本；强工具唯一未完成来自提交引用与工具参数容量问题，不归为模型编译能力不足。

独立固定方案30次组件实验中，四次有依据的直接配置修订均完成且无需新增恢复请求。历史八任务系统比较中，Forge与强工具均完成16次，Forge模型估费低22.9%、耗时接近。其他经验比较保留跨项目增费、失败恢复抵消初始节约和清理建议越界等反例。结果支持构建领域的阶段状态建模、有界动作选择及固定条件方案复用的实用价值，并表明跨项目经验需要进一步核对当前前提和动作目标。结论限于对应任务、版本及样本暴露，不证明任意仓库最优、学习型路由已有效或普遍持续自进化。

首轮离线Harness实验根据九条历史轨迹生成实际规划策略，并完成六项目、两重复、两版本的24次比较。H0/H1主任务完成10/12与11/12，H1在线费用和时间分别高32.9%与18.4%，含离线提案后成本进一步上升。三次未完成暴露共同阶段与目录观察边界，当前不默认采用候选；结果表明Harness更新应针对当前问题并实际比较，不能由更充分的检查或历史轨迹分析自动推断收益。

## Abstract (Working Draft)

Automated building of C/C++ repositories involves dependency preparation, configuration, compilation, and artifact validation. Project differences limit fixed command templates, while delegating every action to a language model can add interaction and repeated exploration. A successful command also does not establish that artifacts, applicable tests, and reproducible delivery satisfy the task. This thesis investigates how current execution state and validated historical experience can guide action selection under a fixed build model.

The method combines model planning, workflow execution, and failure recovery. A planning agent derives dependency, configuration, and build actions from author-provided materials. The workflow tracks stage goals, execution records, and valid progress. Exit codes, logs, observed configuration, and primary artifacts determine whether to continue, apply a bounded direct action, or request an agent-generated revision. Execution resumes from the first changed step. Validation separates primary artifacts, applicable author tests, source preservation, exact delivery, and clean replay under the same image according to the task version. A two-level experience design directly executes validated plans matching the source, image, and task identity, while conditional cross-project guidance supports planning or new recovery tasks when no exact plan exists. Retrieval occurs once per agent task; retrieval, correct adoption, and continual improvement are evaluated separately.

Experiments evaluate systems, state components, recovery interfaces, and experience under distinct versioned conditions. In a 54-run main-build comparison covering nine development-exposed projects, three build systems, and two repetitions, base Forge, experience Forge, and a strong tool agent completed 18/18, 18/18, and 17/18 runs. Base Forge reduced estimated online model cost by 60.5% relative to the tool agent, with 42.2% higher cumulative runtime. Experience Forge reduced online cost by 52.5% and runtime by 52.2% relative to base Forge; however, double-conversion accounted for 96.3% of the runtime difference, limiting claims of stable acceleration. All six exact-plan reuse runs completed actual rebuilding, delivery, and replay without model calls, with 12.1% less runtime than base Forge. Assigning historical plan acquisition and bank creation costs once to this workload made experience deployment more expensive than base online execution. The tool agent's single incomplete run resulted from an incorrect command reference followed by a tool argument-length limit, rather than an established inability to compile the project.

In a separate 30-run fixed-plan component experiment, all four evidence-backed direct configuration revisions completed without additional recovery requests. An earlier eight-task system comparison completed 16 runs in both Forge and the tool agent, with 22.9% lower estimated model cost and similar runtime for Forge. Other experience studies retain increased costs, recovery overhead offsetting initial savings, and an unsafe cleanup recommendation as counterexamples. The findings support the practical value of build-specific state modeling, bounded action selection, and plan reuse under fixed conditions. Cross-project guidance still requires stronger checks of current preconditions and action targets. Claims remain limited to the evaluated task versions and disclosed exposure; they do not establish arbitrary-repository optimality, effective learned routing, or general continual self-improvement.

A first offline Harness update used nine historical trajectories to generate a planning policy and evaluated it in 24 runs across six projects and two repetitions. H0 and H1 completed 10/12 and 11/12 main-build tasks, respectively, while H1 increased online cost by 32.9% and runtime by 18.4%. Proposal cost further increased deployment cost. Three incomplete runs exposed shared stage and directory observation limits. The candidate was therefore retained for analysis rather than adopted by default; the result motivates updates that target current failure modes and undergo explicit comparison.

**Keywords:** automated building; C/C++ repositories; state awareness; action selection; experience reuse; reproducible verification

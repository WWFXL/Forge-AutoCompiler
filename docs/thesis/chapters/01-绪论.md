# 第1章 绪论

## 1.1 研究背景与意义

开源软件仓库是软件复用、程序分析、漏洞验证和自动化测试的重要输入。开展这些工作往往首先需要获得可执行程序或可链接库。对于C/C++项目，源码文件的存在并不意味着能直接完成编译：系统依赖、编译器与构建工具、项目配置选项、生成脚本和测试依赖共同决定最终结果。构建过程还可能生成多个库、程序、示例及测试端点，因此“生成了一个文件”不足以代表完整完成任务。

传统构建工具能够按照给定配置执行依赖关系，但通常不负责理解不完整文档、判断环境差异或解释异常。近年来，大语言模型结合工具执行的Agent被用于仓库级构建与环境配置[1–3]。这类方法可以读取文档、生成命令、观察错误并尝试修复，为降低人工构建成本提供了新的路径。然而，模型具备命令生成能力，并不自动解决何时需要调用模型、怎样保存有效进展、何时应当认为任务完成等系统问题。

实际构建存在两种不同性质的工作。一部分是方案确定后可以直接执行的步骤，例如按照已经选定的配置执行编译与测试；另一部分是必须结合实际反馈判断的步骤，例如依赖发现失败、任务所需配置未开启或交付文件与预期不同。将二者统一交给模型逐条决策，可能增加交互；将二者全部固定为模板，又难以覆盖仓库差异。本文据此研究将阶段化执行与状态驱动决策结合的自动化构建方法。

此外，不同项目可能重复出现相似的构建困难。若每个任务都从零分析，系统无法利用此前成功或失败的探索。固定模型下改进Harness，是与升级模型不同但可能互补的方向。Harness在本文中指支撑Agent工作的工具、上下文、执行控制和经验使用机制。本文进一步研究把具有实际动作与验证记录的历史经验与当前构建状态关联，服务后续规划和恢复，并分别比较原轨迹片段、结构化经验、失败过程提炼、逐条适用性选择及任务后更新。

## 1.2 C/C++仓库自动化构建的关键挑战

### 1.2.1 项目差异与流程结构并存

CMake、Make与Autotools提供不同的项目组织和配置机制。即使两个项目采用同一种构建系统，测试默认开关、依赖版本、配置入口和交付位置也可能不同。由构建系统名称直接选择模板，能够覆盖部分项目，但不能保证满足每个项目的完整目标。另一方面，这些项目通常仍可分解为依赖准备、配置、编译与后续验证等宏观阶段，为Workflow执行提供了可利用的结构。

### 1.2.2 命令成功与目标满足存在差距

配置命令返回0，只说明该次命令按工具定义成功结束，并不保证任务要求的测试或benchmark已经开启。测试入口也可能在没有注册测试时返回成功。库和可执行文件的类型正确，不代表交付集合与指定目标一致。因此，需要区分工具执行状态、项目配置状态与完整任务状态，而不能仅以最后一次退出码判断成功。

### 1.2.3 恢复需要兼顾灵活性与已有进展

异常可能跨越阶段边界。配置时找不到依赖，原因既可能是未安装，也可能是版本不符或搜索路径错误。部分异常可用明确规则处理，其他异常需要Agent诊断。修订依赖或配置后，旧编译与测试结果可能失效；若继续沿用旧状态，会形成错误的完成判断，若总从头重做，又会浪费已经有效的工作。系统需要定义方案变化与进展保留之间的关系。

### 1.2.4 历史经验的可迁移性有限

相同错误文本不一定对应相同原因。旧项目中的绝对路径、包版本或配置选项可能不适用于新环境。经验需要包含触发条件、实际动作和验证范围，并结合当前状态判断适用性。是否能够从已有轨迹中提炼出比原日志更有用的知识，需要独立实验回答，不能从“保存了成功经验”直接推导。

## 1.3 研究问题与主要研究内容

本文的总研究问题是：如何利用当前构建状态与经过验证的历史经验，改善C/C++仓库自动化构建中的动作选择、探索效率与完整任务完成表现？实验在同一组方法比较中保持模型条件一致，使观察到的差异能够围绕方法解释；这并不限制后续使用其他模型检验适用性。

围绕总问题，本文组织四个实验问题。RQ1研究方案驱动的完整系统与强工具Agent之间的完成、模型费用和时间取舍；RQ2研究状态观察、直接动作及失败恢复各自的作用；RQ3研究分层验证能够识别哪些完成缺口；RQ4研究状态关联经验能否改善后续规划与恢复，进一步区分固定经验复用与持续更新的作用。

主要研究内容分为两项。第一项是状态感知动作选择与异常恢复：定义构建任务、阶段和观测，利用真实执行结果与任务目标选择继续、直接修订或Agent恢复，并在方案变化后重新执行受影响部分。第二项是经验驱动Harness改进：实现从轨迹到经验的表示、状态关联检索、适用性判断及任务后追加，并以同一在线模型和基础执行方法进行独立比较。方法实现与实证效果分别陈述，不以研究目标代替效果结论。

## 1.4 主要工作与贡献边界

目前完成的第一项工作是面向构建任务的方案执行与状态决策方法。该方法将项目特定方案、显式任务目标、实际执行记录、受限直接动作、Agent方案修订与重新验证连接起来。当前语义增强主要覆盖具有明确证据的CMake BOOL目标；它是构建领域的方法与系统设计，不是新的通用Agent机制或覆盖全部错误的自动求解器。

目前完成的第二项工作是围绕上述方法组织的实证评价。完整系统比较、固定初始方案消融、恢复开关比较和验证案例承担不同的论证任务。已有结果既包含费用收益，也包含独立规划下状态增强成本更高等混合现象。本文保留这些差异，以限定方法的适用范围，而非追求所有项目、所有指标均占优。

第三项工作是面向构建状态的经验表示与复用研究。实现从成功和失败轨迹提炼条件、阶段、动作、不适用范围及命令证据，以来源族隔离、构建系统过滤和阶段/词项检索辅助当前规划与恢复，并实现只影响后续任务的追加更新。进一步补充真实失败/修订过程，并按当前阶段、归档文件、作者声明和实际错误信号逐条筛选，未确认时允许空经验。两层使用区分同项目可执行方案与跨项目条件建议：前者在匹配源码、镜像和任务要求后省去重复规划，后者依据当前目标与真实失败选择上下文，仍由Agent核对适用性。通过无经验、原轨迹片段、结构化经验、同新库逐条选择、来源事实分离的短动作候选、同项目复用及同库检索比较，分别检验复用、选择与更新。该工作属于构建领域的方法实现与实证研究，不是自动改写整个Harness的通用递归机制；效果和局限以第6章对应独立实验为准。

## 1.5 论文组织结构

第2章介绍构建流程、Agent与相关工作，说明本文定位。第3章定义任务、执行阶段、共同框架与完整完成条件。第4章展开当前状态观测、动作选择和恢复方法，并单列工具辅助局部恢复与交还方法。第5章描述实际经验表示、提炼、检索和任务后更新。第6章给出基础系统、组件、恢复接口和经验比较，并分析分层验证与反向案例。第7章总结结论、局限与后续研究。

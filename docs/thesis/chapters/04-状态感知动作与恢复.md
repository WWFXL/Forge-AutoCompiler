# 第4章 构建状态感知的动作选择与异常恢复

## 4.1 研究动机与问题定义

方案执行需要回答两个不同问题：某条命令是否成功，以及其产生的状态是否满足任务。若只在命令失败时调用Agent，可能错过配置阶段已经出现的目标偏差，直到编译之后才发现遗漏。若对所有状态都调用Agent，又可能失去方案执行减少交互的意义。因此，本章研究在明确证据下进行受限动作选择，并将复杂或未知问题交给Agent。

本章4.2—4.5描述用于既有系统和状态消融的方法；对应恢复Agent读取源码和日志后返回修订方案，由Workflow执行。4.6描述2026-11-02实现的工具辅助局部恢复版本，新增效果应使用独立比较，不将其工具能力当作既有实验条件。

本文不试图穷举C/C++的所有构建错误。直接动作的范围由可检查前提限定，超出范围的问题交接Agent。该取舍使系统可以先在明确任务语义上形成可检验方法，而不依赖持续扩张的异常正则与修复模板。

## 4.2 状态观测与目标偏差表示

### 4.2.1 执行状态与语义状态

为组织说明，记时刻t的状态为s_t=(P_t,F_t,O_t,G,B_t)：P_t是当前方案，F_t是仍有效的执行进展，O_t是实际观测，G是固定任务目标，B_t是剩余资源。该元组是对当前数据的论文抽象，具体字段仍由实现中的方案、命令记录、配置观测及预算对象承载，不是训练得到的隐变量表示。

F_t包含已经成功且与当前方案一致的步骤及命令身份；O_t包含退出码、超时、日志和适用配置缓存。对无法从工具结果确定的语义，系统保留未知，不把模型猜测直接作为状态事实。

阶段与状态具有不同含义。“configure”表示当前执行角色；“配置满足目标”表示实际结果与任务要求之间的关系。同一配置阶段可以成功且满足，也可以成功但偏离，还可以由于缺少缓存而无法判断。表4-1说明当前方法中主要决策状态。

| 状态 | 实际依据 | 当前选择 |
|---|---|---|
| 步骤就绪 | 前置步骤成功且执行记录仍有效 | 执行方案动作 |
| 步骤成功 | 实际退出结果与必要输出满足要求 | 记录进展，满足额外条件后推进 |
| 配置满足 | 实际缓存符合支持的显式目标 | 继续编译 |
| 配置偏离且可修订 | 作者选项声明、真实BOOL值和来源等条件成立 | 生成一次直接配置修订 |
| 配置未知或无法直接修订 | 缓存/变量缺失、类型或来源不支持等 | 交Agent分析并返回方案 |
| 执行失败或预期缺失 | 非零退出、超时或必要输出不满足 | 交Agent，携带实际日志 |
| 方案修订 | 新旧步骤存在变化 | 失效受影响后缀，重新执行 |
| 方案执行完毕 | 当前方案的所有步骤成功 | 进入完整任务验证 |
| 资源不足或状态不一致 | 剩余时限、额度或执行历史不足以继续 | 停止并保存已观察结果 |

### 4.2.2 显式配置目标提取

当前实现只提取固定任务中能够静态确定的配置布尔要求。已支持形式包括配置检查脚本中的字面requirements字典及特定显式静态库默认约束。提取过程不运行验证脚本以猜测目标，也不解释任意Python、自然语言版本范围或未声明的功能要求。

目标可以表示为g=(p,k,b)，其中p是配置缓存相对路径，k是选项名，b是期望布尔值。原目标检查命令的摘要用于关联约束来源。同一路径与变量出现相反要求时，应拒绝矛盾任务，而不是任意选择一个值。

### 4.2.3 实际观测与满足性判断

观察器读取真实执行后生成的CMakeCache，保存原字节摘要、变量类型、实际值及源码目录。对具有可解释值的目标，比较其布尔含义与期望；证据缺失时记为unknown。若任一目标明确偏离，整体标为violated；无偏离但存在未知时，整体保持unknown；全部可判断且一致时标为satisfied。

执行器在最后配置步骤成功后，以及首次编译前检查适用目标。没有可适用目标的任务按普通阶段流程执行，不将其记为配置语义已验证通过。Make/Autotools当前不具有与此相同的缓存语义增强。

## 4.3 动作空间与选择条件

本章控制器的动作可以概括为执行已规划步骤、继续推进、直接修订、交接Agent、提交验证和停止。实际初始命令与复杂恢复方案由模型生成，直接动作的触发条件由代码检查。该控制器不是学习型路由，也不根据错误关键词无限扩展规则集合。

直接修订要求实际目标已经偏离、待改变量是作者声明的BOOL选项、缓存属于同一根项目及同一构建上下文，且观测仍对应当前证据。HAVE_*等依赖探测结果不作为可强设选项。当前任务尚未使用过直接修订时，系统才可以生成一次明确的CMake配置动作，其余情况转交原恢复Agent。

例如任务要求benchmark为ON，实际缓存为OFF，且作者CMake文件存在对应option，系统可追加如下形式的命令：

```bash
cmake -S /workspace/repo -B /workspace/repo/build -D选项名:BOOL=ON
```

该命令是示意，真实路径、变量和值由本任务证据确定。修订后必须重新观测目标，再继续编译。系统不把缺包、版本冲突、未知路径或链接失败硬映射到安装命令；这些情况仍交Agent。

规则的价值由其适用前提和比较结果决定，而不是数量。已知选项纠偏可以低成本执行，但覆盖范围有限。第6章将使用固定方案消融评价该范围中的作用，并保留独立规划下没有总体优势的结果。

## 4.4 基于证据的Agent方案修订

超出直接动作范围时，执行器构造交接，提供任务、当前方案、失败步骤、权威命令记录、日志与配置状态、剩余资源等信息。Agent可以读取仓库及相关日志，返回完整修订方案和修改理由。完整方案便于执行器比较新旧步骤，当前实现不允许只用一句自然语言说明替代可执行修订。

修订必须保留任务身份与固定要求，不能改变原测试、源码约束或指定交付集合。依赖或配置发生变化时，模型应明确需要清理的缓存和旧产物。未改变任何步骤的方案不能通过重复执行同一失败来消耗资源。

Agent返回修订不等于问题已经解决。Workflow执行新动作后形成新证据，如果仍失败，可在剩余资源允许时再次交接。初始规划和后续恢复可能多次调用同一模型；系统减少的是正常路径上的不必要决策，并不保证每个项目只发生一次模型请求。

在当前实验中，交接次数、模型请求、命令和时间均受对应协议约束。达到限制时保留未完成，不通过删测试、修改原源码或回填结果宣告完成。

## 4.5 修订后的失效传播与后缀重执行

设旧方案P=(a1,…,an)，新方案P'=(a'1,…,a'm)。实现逐步比较动作标识、命令、角色、工作目录、前置关系与必要输出，找到最长相同前缀长度k。只有前k步中已经成功的记录能够保留，其后记录失效，新方案从相应位置继续。

这种策略比总从头执行保留更多进展，但比任意依赖图最小重算保守：即使某些后续步骤实际上不受影响，当前实现仍按变化后缀重做。其目的在于让方案比较、执行历史与重新验证保持清晰关系，不宣称得到全局最小重执行集合。

需要再次强调，逻辑失效不等于物理清理。若修改配置但保留了旧缓存，仍可能出现状态残留。新方案应显式清理受影响内容，最终由干净重放检查完整执行配方是否足以重新获得结果。

算法4-1概括当前基础方法。观测与动作选择中适用范围外的问题保持交接，不伪装为确定状态。

```text
输入：固定任务T、初始方案P、运行资源B
初始化：有效进展F为空，直接修订未使用
循环，直到完整完成或停止：
    若资源不足或执行历史不一致：保存结果并停止
    若存在就绪步骤：
        执行步骤，保存实际命令及结果
        在适用配置检查点观测显式目标
        若步骤成功且无需恢复：更新F，继续
        否则形成包含实际证据的交接
    否则若方案全部步骤完成：
        提交完整验证与干净重放
        若通过并完成清理：返回完整完成
        否则按可恢复条件形成交接或停止
    若交接满足直接修订条件且尚未使用：生成一次修订P'
    否则：由恢复Agent返回修订P'及理由
    校验任务与验证要求保持
    比较P和P'，保留未变成功前缀，失效变化后缀
    令P为P'，重新观测并执行
```

## 4.6 工具辅助局部恢复与控制权交还

基础恢复方式要求Agent先返回完整方案，由Workflow执行，再根据结果决定是否再次交接。工具辅助版本允许Agent在同一次交接中修订方案、执行恢复所需动作并观察反馈。它仍通过同一方案执行器运行真实容器命令，复用退出结果、源码保持、配置观测、资源及复现配方；原测试与交付由Workflow继续。本节能力已实现，效果按第6章独立比较评价。

### 4.6.1 恢复目标与工具

交接目标取异常步骤的构建角色，即依赖、配置或编译；原测试及交付异常以恢复构建为目标。恢复可返回前置阶段，例如配置异常可先准备依赖，再重新配置。它并非只准执行一条失败命令，也不将全部后续流程永久交给Agent。

Agent保留目录、源码与日志只读工具，并增加三个工具：

| 工具 | 输入与实际作用 |
|---|---|
| revise_recovery_plan | 接收完整ObservedBuildActions；装配固定测试及交付，保留有效前缀并失效变化后缀 |
| execute_recovery_step | 执行当前方案下一就绪动作，角色不超过恢复目标；返回执行及日志收据，完整结果进入后续状态包 |
| return_to_workflow | 检查恢复目标及前置动作的成功记录和适用配置目标，交还仍有效的实际进展 |

这里开放的是已纳入修订方案的构建动作，底层使用容器bash；没有新增任意诊断Shell或联网工具。需要的安装和配置修复必须写入完整方案，才能在干净重放中保留，避免仅让原容器偶然可用。

### 4.6.2 交还条件与执行进展

在恢复目标及前置动作均存在有效成功记录、适用配置目标满足，并且本次交接至少有一次修订与真实命令执行时，系统才允许交还。Agent不能使用普通文本自报成功代替这些条件。交还后Workflow继续尚未完成的步骤；局部执行成功的命令成为有效进展，不再自动重复。

若修订改变配置或更早动作，旧编译和测试记录按4.5节失效，不能沿用。局部工具不直接执行固定测试或交付，不允许通过改裁判结束任务。后续又出现异常时可以再次局部交接，但仍消耗同一任务的交接、命令、Token和时间额度。

相同动作及相同前置执行证据不重复尝试；输入错误反馈给Agent以便显式纠正，源码变化、外部状态变化或计量异常则向上传播。没有达到交还条件时保留失败，不自动切回另一种恢复方式补救。

算法4-2给出局部恢复的控制过程。这里的“局部”由可执行角色及交还条件约束，可以包含多个前置步骤；它不表示Agent只能输出一条命令。

```text
输入：活动交接H、当前方案P、有效进展F、实际观测O、剩余资源B
由异常角色确定恢复目标R；测试/交付异常的R取build
在H有效且B允许时：
    向Agent提供共同任务、当前方案、真实状态及最近执行结果
    若Agent提交方案修订：
        验证固定任务与动作约束；保留未变成功前缀，失效变化后缀
    若Agent请求执行步骤a：
        要求已完成实际修订，a是下一就绪步骤且角色不超过R
        拒绝相同动作与相同前置执行证据的重复尝试
        通过共同执行器运行a，记录退出结果、日志及配置观测
        成功则更新有效进展F，失败则保留反馈供再次修订
    若Agent请求交还：
        要求R及前置步骤有有效成功记录、适用配置目标满足
        要求本次交接有实际修订与执行
        关闭H，将P、F及实际记录交还Workflow，结束恢复
未满足交还条件且无法继续：保留未完整结果并停止
```

该过程把控制返回与执行事实绑定。Agent返回后，阶段进展可以比调用前更靠后；Workflow依据已记录的成功动作继续，原测试与最终交付仍须执行。它区别于只返回计划而尚无新增执行事实，也区别于让Agent自行宣告整个任务完成。

### 4.6.3 比较所回答的问题

这一增强的潜在收益是减少跨Workflow的往返，并利用连续工具反馈完成修复；其代价是提交方案、逐步执行及交还也需要模型交互。两种方式存在明确取舍，不能预设局部工具一定更省。本轮比较将初始方案、模型、目标观察及验收保持一致，比较恢复工具与交互方式的组合。它不单独识别工具数量或控制器的纯因果，也不代表经验自进化已经实现。方案式恢复沿用最多8轮探索、可提前提交、达到上限后强制提交的策略，局部恢复采用连续工具交互；全局资源相同不等于局部交互策略完全相同。

## 4.7 案例、开销与适用范围

在既有snappy案例中，任务要求保留benchmark，但自然初始方案设置为OFF。配置命令成功后，观察器保存实际缓存，确认选项声明和偏差，追加ON修订。随后重新观测、编译、原测试、精确交付和干净重放均完成，未增加恢复模型请求。该案例体现命令成功与目标满足的区别。

配置观测需要读取缓存和作者选项声明，会产生本地开销；直接修订也需要再次配置。其收益取决于避免了多少无效编译和模型恢复。已有正常方案层没有额外交接，不意味着所有项目的检查开销为零。已有系统比较中配置均满足、直接修订未触发，也不能把系统总费用收益归给该动作。

当前方法尚不覆盖任意配置语言、复杂版本约束、多根工程或一般依赖诊断。它对显式BOOL场景提供具体可执行方法，对超范围情况保留Agent。下一章拟利用这些状态与动作记录提炼经验，进一步研究跨任务复用。

### 4.7.1 主构建异常的事实观察与受限语义路由

2026-11-05的新增实现面向简洁主构建任务，将事实观察、原因选择与动作执行分开。事实层读取当前阶段及目的、实际命令/退出结果、关键日志、实际配置和主要产物状态。它不因模型输出“完成”而覆盖非零退出或产物缺失。选择层仅在异常或结果不确定且存在有依据的候选时工作，执行层仍由Workflow记录实际结果。正常路径无需分类模型；无可靠候选直接交恢复Agent调查。

候选由作者声明和当前方案提供，目前仅实现三类：作者声明最低CMake版本后的工具升级、当前配置缺失或失败后的配置后缀恢复、产物观察未完成后的补充观察。规则和Jev共享候选及同一Flash恢复路径。规则根据有限明确日志选择；Jev将相同状态包作为输入，一次结构化请求分别选择状态类别和已有动作。状态类别包括阶段完成、前置缺失、执行失败、证据不足，动作选择包括当前候选及Agent。Jev不生成Shell，不决定最终验收，不使用旧控制器的校准阈值；它是待评价的语义选择组件，不是已经证明有效的学习型构建状态模型。

例如double-conversion配置日志明确要求CMake至少3.29、实际为3.28.3，配置退出1。事实层记录前置工具不足的线索，候选层根据作者最低版本声明生成安装新版工具及重做配置/构建的方案。只有选择该动作后实际执行成功，配置与构建进展才能更新。未知依赖、版本冲突或无候选的问题仍交恢复Agent，而不扩写穷尽所有错误的规则库。每槽最多尝试两个不同局部动作，局部失败保留，后续可转Agent；同一动作不自动重试。

两条零Provider真实工程路径支持变量命令修复和规则恢复链可执行。E49正式比较的首次Jev请求被服务以权限错误拒绝，未产生选择结果，因此目前不能从真实比较支持语义选择的准确性、恢复收益或成本优势。有限规则和事实观测仍是可用基础，Jev增量必须由后续独立证据回答。

共同底座对配置观察作如下补充：任务的初始构建系统信息保持不变，观察器跟随实际执行的构建入口及目录；明确改走Make或SCons后，不继续以原CMake Cache作为阶段要求。观察不适用不等于构建完成，主要产物仍需独立检查。生成物重置通过标准输入传递长脚本及保护名单，避免单参数长度限制；严格Shell、原文件保护和重放保持。两项均为工程修复，在第5章H0/H1中共同使用，不计为自动优化收益。

## 4.8 本章小结

# 第4章 构建状态感知的动作选择与异常恢复

## 4.1 研究动机与问题定义

方案执行需要回答两个不同问题：某条命令是否成功，以及其产生的状态是否满足任务。若只在命令失败时调用Agent，可能错过配置阶段已经出现的目标偏差，直到编译之后才发现遗漏。若对所有状态都调用Agent，又可能失去方案执行减少交互的意义。因此，本章研究在明确证据下进行受限动作选择，并将复杂或未知问题交给Agent。

本章4.2—4.5描述已实现且用于现有实验的方法；4.6描述2026-11-02讨论形成的工具辅助局部恢复设计，尚未实现或获得效果证据。当前恢复Agent读取源码和日志后返回修订方案，由Workflow执行。不能将后续设计的工具能力当作既有实验条件。

本文不试图穷举C/C++的所有构建错误。直接动作的范围由可检查前提限定，超出范围的问题交接Agent。该取舍使系统可以先在明确任务语义上形成可检验方法，而不依赖持续扩张的异常正则与修复模板。

## 4.2 状态观测与目标偏差表示

### 4.2.1 执行状态与语义状态

为组织说明，记时刻t的状态为s_t=(P_t,F_t,O_t,G,B_t)：P_t是当前方案，F_t是仍有效的执行进展，O_t是实际观测，G是固定任务目标，B_t是剩余资源。该元组是对当前数据的论文抽象，具体字段仍由实现中的方案、命令记录、配置观测及预算对象承载，不是训练得到的隐变量表示。

F_t包含已经成功且与当前方案一致的步骤及命令身份；O_t包含退出码、超时、日志和适用配置缓存。对无法从工具结果确定的语义，系统保留未知，不把模型猜测直接作为状态事实。

阶段与状态具有不同含义。“configure”表示当前执行角色；“配置满足目标”表示实际结果与任务要求之间的关系。同一配置阶段可以成功且满足，也可以成功但偏离，还可以由于缺少缓存而无法判断。表4-1说明当前方法中主要决策状态。

| 状态 | 实际依据 | 当前选择 |
|---|---|---|
| 步骤就绪 | 前置步骤成功且执行记录仍有效 | 执行方案动作 |
| 步骤成功 | 实际退出结果与必要输出满足要求 | 记录进展，满足额外条件后推进 |
| 配置满足 | 实际缓存符合支持的显式目标 | 继续编译 |
| 配置偏离且可修订 | 作者选项声明、真实BOOL值和来源等条件成立 | 生成一次直接配置修订 |
| 配置未知或无法直接修订 | 缓存/变量缺失、类型或来源不支持等 | 交Agent分析并返回方案 |
| 执行失败或预期缺失 | 非零退出、超时或必要输出不满足 | 交Agent，携带实际日志 |
| 方案修订 | 新旧步骤存在变化 | 失效受影响后缀，重新执行 |
| 方案执行完毕 | 当前方案的所有步骤成功 | 进入完整任务验证 |
| 资源不足或状态不一致 | 剩余时限、额度或执行历史不足以继续 | 停止并保存已观察结果 |

### 4.2.2 显式配置目标提取

当前实现只提取固定任务中能够静态确定的配置布尔要求。已支持形式包括配置检查脚本中的字面requirements字典及特定显式静态库默认约束。提取过程不运行验证脚本以猜测目标，也不解释任意Python、自然语言版本范围或未声明的功能要求。

目标可以表示为g=(p,k,b)，其中p是配置缓存相对路径，k是选项名，b是期望布尔值。原目标检查命令的摘要用于关联约束来源。同一路径与变量出现相反要求时，应拒绝矛盾任务，而不是任意选择一个值。

### 4.2.3 实际观测与满足性判断

观察器读取真实执行后生成的CMakeCache，保存原字节摘要、变量类型、实际值及源码目录。对具有可解释值的目标，比较其布尔含义与期望；证据缺失时记为unknown。若任一目标明确偏离，整体标为violated；无偏离但存在未知时，整体保持unknown；全部可判断且一致时标为satisfied。

执行器在最后配置步骤成功后，以及首次编译前检查适用目标。没有可适用目标的任务按普通阶段流程执行，不将其记为配置语义已验证通过。Make/Autotools当前不具有与此相同的缓存语义增强。

## 4.3 动作空间与选择条件

本章控制器的动作可以概括为执行已规划步骤、继续推进、直接修订、交接Agent、提交验证和停止。实际初始命令与复杂恢复方案由模型生成，直接动作的触发条件由代码检查。该控制器不是学习型路由，也不根据错误关键词无限扩展规则集合。

直接修订要求实际目标已经偏离、待改变量是作者声明的BOOL选项、缓存属于同一根项目及同一构建上下文，且观测仍对应当前证据。HAVE_*等依赖探测结果不作为可强设选项。当前任务尚未使用过直接修订时，系统才可以生成一次明确的CMake配置动作，其余情况转交原恢复Agent。

例如任务要求benchmark为ON，实际缓存为OFF，且作者CMake文件存在对应option，系统可追加如下形式的命令：

```bash
cmake -S /workspace/repo -B /workspace/repo/build -D选项名:BOOL=ON
```

该命令是示意，真实路径、变量和值由本任务证据确定。修订后必须重新观测目标，再继续编译。系统不把缺包、版本冲突、未知路径或链接失败硬映射到安装命令；这些情况仍交Agent。

规则的价值由其适用前提和比较结果决定，而不是数量。已知选项纠偏可以低成本执行，但覆盖范围有限。第6章将使用固定方案消融评价该范围中的作用，并保留独立规划下没有总体优势的结果。

## 4.4 基于证据的Agent方案修订

超出直接动作范围时，执行器构造交接，提供任务、当前方案、失败步骤、权威命令记录、日志与配置状态、剩余资源等信息。Agent可以读取仓库及相关日志，返回完整修订方案和修改理由。完整方案便于执行器比较新旧步骤，当前实现不允许只用一句自然语言说明替代可执行修订。

修订必须保留任务身份与固定要求，不能改变原测试、源码约束或指定交付集合。依赖或配置发生变化时，模型应明确需要清理的缓存和旧产物。未改变任何步骤的方案不能通过重复执行同一失败来消耗资源。

Agent返回修订不等于问题已经解决。Workflow执行新动作后形成新证据，如果仍失败，可在剩余资源允许时再次交接。初始规划和后续恢复可能多次调用同一模型；系统减少的是正常路径上的不必要决策，并不保证每个项目只发生一次模型请求。

在当前实验中，交接次数、模型请求、命令和时间均受对应协议约束。达到限制时保留未完成，不通过删测试、修改原源码或回填结果宣告完成。

## 4.5 修订后的失效传播与后缀重执行

设旧方案P=(a1,…,an)，新方案P'=(a'1,…,a'm)。实现逐步比较动作标识、命令、角色、工作目录、前置关系与必要输出，找到最长相同前缀长度k。只有前k步中已经成功的记录能够保留，其后记录失效，新方案从相应位置继续。

这种策略比总从头执行保留更多进展，但比任意依赖图最小重算保守：即使某些后续步骤实际上不受影响，当前实现仍按变化后缀重做。其目的在于让方案比较、执行历史与重新验证保持清晰关系，不宣称得到全局最小重执行集合。

需要再次强调，逻辑失效不等于物理清理。若修改配置但保留了旧缓存，仍可能出现状态残留。新方案应显式清理受影响内容，最终由干净重放检查完整执行配方是否足以重新获得结果。

算法4-1概括当前基础方法。观测与动作选择中适用范围外的问题保持交接，不伪装为确定状态。

```text
输入：固定任务T、初始方案P、运行资源B
初始化：有效进展F为空，直接修订未使用
循环，直到完整完成或停止：
    若资源不足或执行历史不一致：保存结果并停止
    若存在就绪步骤：
        执行步骤，保存实际命令及结果
        在适用配置检查点观测显式目标
        若步骤成功且无需恢复：更新F，继续
        否则形成包含实际证据的交接
    否则若方案全部步骤完成：
        提交完整验证与干净重放
        若通过并完成清理：返回完整完成
        否则按可恢复条件形成交接或停止
    若交接满足直接修订条件且尚未使用：生成一次修订P'
    否则：由恢复Agent返回修订P'及理由
    校验任务与验证要求保持
    比较P和P'，保留未变成功前缀，失效变化后缀
    令P为P'，重新观测并执行
```

## 4.6 工具辅助局部恢复的拟增强设计

> 本节为设计方案，尚未实现或获得比较结果。它不能作为第6章既有实验中恢复Agent的能力说明。

仅返回修订方案时，Agent无法在本次恢复内连续执行诊断。若缺依赖、版本或路径问题需要逐步排查，可能发生多次“返回方案—执行—失败—再次交接”。拟增强方法允许Agent通过统一容器工具执行检查与修复，读取反馈，在恢复到明确条件后交还Workflow。

恢复边界由当前异常的目标定义，不机械限制在一个宏观阶段。例如配置失败可要求恢复到“配置成功且目标满足”，允许先回到依赖阶段，再重新配置。Agent无需继续完成全部后续测试和交付，达到交还条件后由系统确认状态并恢复正常执行。

返回内容应同时包含实际命令、观察结果、修改影响、当前满足条件和更新方案。已经有效完成的步骤不应无理由重复，受影响的旧结果不能继续使用。安装与配置等有效修复还需进入复现配方，避免原容器可用而干净重放缺少依赖。该接口可使局部恢复与当前执行记录、后缀失效机制衔接。

这项设计的待验证问题是：连续工具反馈能否提高恢复完成或减少交接成本，以及额外诊断是否会抵消收益。需要与返回方案方式在相同任务或可恢复失败起点上比较，不能仅因为工具更丰富就预设更优。

## 4.7 案例、开销与适用范围

在既有snappy案例中，任务要求保留benchmark，但自然初始方案设置为OFF。配置命令成功后，观察器保存实际缓存，确认选项声明和偏差，追加ON修订。随后重新观测、编译、原测试、精确交付和干净重放均完成，未增加恢复模型请求。该案例体现命令成功与目标满足的区别。

配置观测需要读取缓存和作者选项声明，会产生本地开销；直接修订也需要再次配置。其收益取决于避免了多少无效编译和模型恢复。已有正常方案层没有额外交接，不意味着所有项目的检查开销为零。已有系统比较中配置均满足、直接修订未触发，也不能把系统总费用收益归给该动作。

当前方法尚不覆盖任意配置语言、复杂版本约束、多根工程或一般依赖诊断。它对显式BOOL场景提供具体可执行方法，对超范围情况保留Agent。下一章拟利用这些状态与动作记录提炼经验，进一步研究跨任务复用。

## 4.8 本章小结

本章给出由实际记录产生状态、比较显式目标、选择受限直接修订或Agent恢复的方法，定义方案变化后的前缀保留与后缀重执行。当前已有证据支持有限配置场景中的机制作用，不能推出开放世界错误均可规则处理。工具辅助局部恢复将作为基础方法增强单独评价，经验方法则在下一章建立于同一状态与执行记录之上。

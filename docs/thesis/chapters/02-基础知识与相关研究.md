# 第2章 基础知识与相关研究

## 2.1 C/C++构建流程与构建系统

C/C++仓库构建通常涉及工具链与依赖准备、项目配置、编译链接、测试运行和产物交付。配置过程决定编译目标、依赖位置、构建类型及可选功能；编译和链接将源文件转换为目标文件、库或可执行程序；测试需要额外的目标生成与运行条件。某些项目还需要在配置之前生成辅助脚本，因此宏观阶段与实际命令之间并非严格一一对应。

CMake通过项目描述生成面向本机构建工具的执行文件，并在构建目录保存缓存。配置开关能够控制是否生成测试、示例或benchmark等目标[10]。Make根据规则、目标与先决条件执行命令，但不同项目可能通过变量选择目标和依赖路径[11]。Autotools项目可能先执行bootstrap或autoreconf生成configure等文件，再配置和编译[12]。因此，自动化系统需要识别构建系统，同时读取项目自身约定。

构建依赖也有不同含义。系统包或外部库是环境依赖，源文件与目标文件之间是构建图依赖，配置开关与功能目标之间则是任务约束关系。依赖已安装但构建工具无法发现，与依赖根本不存在，需要不同处理。本文不把这些问题合并成单一“缺依赖”类别，也不声称已提供统一依赖解析器。

## 2.2 工具Agent、方案执行与Harness

工具Agent通过模型调用工具、读取反馈并决定后续动作。其优势是能够适应不确定情况，但每次决策可能引入模型请求与上下文开销。方案驱动执行则先获得一组有序或具有依赖关系的动作，再由执行器推进；其优势是正常步骤可直接运行，但初始方案错误和环境变化仍需要恢复。

这两种形式可以在同一系统中组合。Workflow负责阶段进度与执行记录，Agent负责方案生成和超出直接动作范围的异常分析。选择何时交接、交接携带哪些证据、返回后怎样恢复进度，属于Harness设计的一部分。本文用“规划角色”和“恢复角色”描述两类职责，不预设它们必须使用不同模型或相互对话。

当前基础方法的Agent在恢复时返回方案，实际修复由Workflow执行。拟研究的工具辅助局部恢复则允许Agent运行检查与修复命令，在恢复到明确条件后交还控制权。这两种方式都可以保留总体Workflow结构，其差别在于恢复过程中的决策与执行反馈由谁连续组织。

## 2.3 自动化构建与环境配置研究

CXXCrafter针对C/C++开源软件构建设计基于大模型的Agent系统，包括项目信息分析、构建描述生成及反馈修订[1]。其研究说明仓库级构建不能仅靠一条通用命令解决，也为本文的外部系统参考提供来源。本文不将“用Agent修复C++构建”作为首次创新。实验使用可运行社区快照，工具、反馈和验收与原论文并非完全相同，因而不能把本地观察解释为论文原版能力排名。

CompileAgent研究工具集成的仓库级编译，并包含流程化策略及策略/模块评价[2]。BuildBench面向真实开源软件编译组织基准和Agent评价，其方法包含生成构建指令后执行与反馈修复[3]。这些先例意味着“先规划再执行”与“Flow-based编排”本身不足以成为独占创新表述。本文更具体的问题是：怎样把任务目标与实际构建状态纳入动作选择，以及修订后怎样保存和重建有效进展。

Repo2Run研究代码仓库可执行环境的自动构建，涉及状态转移和Dockerfile合成[4]。其主要任务生态与测试终点不同于本文C/C++任务。比较相关工作时，应当同时说明输入对象、允许修改的文件、测试成功定义及交付要求，避免直接排列不同论文的成功率。

表2-1给出这些工作的用途与本文需要区分的范围。它是代表性方法比较，不是对全部研究的穷尽性综述。

| 工作 | 可借鉴内容 | 与本文比较时需区分的条件 |
|---|---|---|
| CXXCrafter | 项目解析、构建描述生成、反馈修订与成本评价 | 原论文与社区快照、源码修改政策、反馈循环和判定差异 |
| CompileAgent | 流程策略、工具集成和组件评价 | 不将Workflow与工具调用本身作为首次设计 |
| BuildBench | 仓库级任务、构建指令执行与基准组织 | 产物名等成功定义不等同于本文完整原测试和重放 |
| Repo2Run | 环境构建、状态转移和测试执行 | 语言生态、任务范围及测试完成含义不同 |

## 2.4 依赖分析、构建状态与验证

DockerizeMe通过知识与分析推断Python代码片段所需环境依赖[5]，表明依赖映射与环境构建可以形成专门研究对象。EChecker研究增量构建中的依赖错误[6]，关注构建关系对正确增量执行的影响。前者不是C/C++仓库完整构建，后者也不是缺失系统包安装。它们分别提示本文应描述依赖知识和状态失效，而不能把已存在的文件依赖方法直接等同为环境恢复算法。

本文的状态控制关注实际执行记录与任务目标之间的关系。阶段执行成功只是证据之一；配置是否包含所需目标、测试是否真正运行、产物集合是否完整、重放是否使用完整配方，分别对应不同的任务条件。验证层之间存在关联，但其结果不必形成简单串行漏斗。例如测试已成功，后续配置改变可能使其失效；交付文件存在，也可能没有完整记录其生成步骤。

因此，本文将分层验证用于界定完成条件和解释具体缺口，而不把它表述为新的程序等价性证明或跨平台可复现保证。同镜像的字节一致重放是较强的操作条件，可能因时间宏等原因拒绝功能正常的产物，其意义与局限需要同时报告。

## 2.5 Agent经验学习与技能复用

Harness²探索在模型权重保持不变时改进Agent执行支撑，并包含跨任务经验的组织与使用[7]。ExpeL研究Agent对经验进行提取和利用[8]；Voyager以技能积累支持后续行为[9]。这些工作说明历史轨迹、经验与技能复用具有一般先例，本文不应把添加外部记忆本身描述为通用机制首创。

构建领域的具体难点在于经验与环境条件紧密相关。一个路径修复可能只在特定安装目录有效，一个配置开关可能只存在于某个版本，而成功运行的轨迹可能依赖工作区中未记录的生成物。因此，拟研究经验应显式关联任务目标、构建系统、实际状态、动作及验证范围。后续任务需重新判断适用性，而不是直接复用旧命令。

固定经验检索与持续改进也需要区分。前者可以通过无经验与有经验比较评价；后者需要在相同初始经验和任务顺序下比较固定库与更新库，并避免读取未来结果。本文第5章围绕该区分提出设计，第6章将对应实验留为待完成内容。

## 2.6 本文定位与本章小结

本文在已有方案执行、工具Agent和经验机制基础上，研究自动化编译领域的状态与动作组织。已有方法把显式配置目标、实际缓存观测、受限修订、Agent回退和后缀重执行连接起来；拟研究方法进一步利用相同状态表示组织经验，以改善后续决策。

现有贡献主要属于构建领域方法适配、系统设计和实证评价。当前没有学习型路由、任意依赖推断或自动改写核心Harness代码的实现。下一章将先定义共同任务和框架，再在第4、5章分别展开状态决策与经验改进。

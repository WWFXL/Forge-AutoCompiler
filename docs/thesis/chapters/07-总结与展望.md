# 第7章 总结与展望

## 7.1 研究工作与主要结论

本文围绕C/C++仓库构建中的项目差异、执行不确定性与重复探索，研究状态感知动作选择和历史轨迹驱动的Harness更新。系统将项目特定方案与通用执行流程分开：规划Agent生成依赖、配置和编译动作，Workflow保存真实执行记录，状态选择器根据目标与实际观测选择推进、直接修订或Agent恢复。修订后保留有效前缀、重新执行受影响后缀，独立检查确认主要产物与可复现交付。

第一，阶段化方案执行能够减少正常路径的模型交互，但模型成本和时间需要分别评价。九项目54次主构建比较中，基础Forge、经验Forge与强工具Agent完成18/18、18/18和17/18；基础模型费低60.5%，累计时间高42.2%。历史八任务比较中，Forge与强工具均完成16次，Forge费用低22.9%，时间接近。其价值在于将确定步骤交给执行器，把模型投入集中在项目分析和异常处置。

第二，状态观察需要与可执行动作相结合。固定初始方案的30次消融中，四次有充分证据的配置直接修订均完成，无新增恢复请求；只提前观察而仍由Agent处理，并未取得相同费用收益。五任务恢复开关比较将完整完成从2/5增加到4/5，同时增加投入。分层验证进一步识别了配置遗漏、测试未注册、配方缺少依赖及验证入口不适配等不同问题。方法据此管理任务进展，而非仅以最后一次命令退出码结束构建。

第三，历史构建经验应按复用关系使用。同源码、镜像和任务下的成功方案可直接执行；E50六次精确复用均零模型调用，实际重建与交付通过，时间比重新规划低12.1%。跨项目经验则需要核对当前前提和动作目标。已有比较既有局部节约，也有额外读取、恢复及建议误用；经验的选择、实际采用与净收益是连续但不同的环节。费用评价同时考虑在线使用、原方案获取和经验库提炼。

第四，Harness更新应根据完整执行轨迹分解效果来源。前两轮提示候选呈现更多完成与更高投入，或初始节约被恢复抵消的现象。H2初始费低18.2%、总费高87.5%，并暴露最终方案遗漏必要依赖的重建失败。这些观察推动更新从单纯调整提示，扩展到工具执行机制。

E57进一步在12项目上分开比较P0旧工具行为、P0工具执行约束与P4同约束，共36次。主构建及可复现交付完成数为10/12、11/12和10/12。工具约束组少19次请求、总费低14.9%，但节约集中困难项目，共同完成的10项目费用反而高85.4%。P4在其中8项目低费，合计费用低38.0%，却因open62541与libffi的额外投入使总费高39.7%。本轮将P0工具约束保留为后续基线候选，P4暂不直接替换。采用决定由全分母完成、初始与恢复成本共同支持，而非由提示长度或多数项目低费单独决定。

本文由此形成同一证据链上的两类工作：任务内以状态组织执行和恢复，任务间以历史轨迹诊断并评价Harness更新。前者提供可解释的控制与结果记录，后者利用这些记录改进后续Agent的工作方式。

## 7.2 研究局限

直接配置动作主要覆盖显式CMake BOOL目标，简洁主构建入口还支持少量有作者声明和日志依据的局部动作。复杂版本冲突、依赖路径和工具链问题仍主要依赖Agent，保守后缀重执行也可能重复部分实际未受影响的步骤。Jev比较在首次异常请求遇到服务权限错误，未获得语义选择响应。

项目数量、历史开发接触和每项目运行次数限制了结果推广。E57各组每项目仅一次，恢复过程含模型波动；工具拒绝也只在open62541实际触发。当前观察说明候选在本批任务中的取舍，尚需更多独立项目检验稳定性。历史严格字节重放与后续成功重建采用不同标准，各批结果按原任务分别使用。

跨项目经验对自然语言前提、工具版本和动作目标身份的核对仍不充分。同项目复用以固定身份为基础，跨版本迁移需要额外验证。离线Harness更新中的研究者诊断、候选选择和工程维护投入也需与Token费用区分，已有在线费用节约并不代表从零部署必然更便宜。

## 7.3 后续研究

后续优先研究困难项目中的准备与恢复。libffi表明，生成脚本前的宏和工具链条件需要更准确的当前证据；open62541表明，依赖准备应围绕主要构建目标，避免不必要的外置依赖操作。候选应保留成功路径上的简洁性，同时针对这些明确失败提出改进，并在固定模型的新项目比较中检验。

经验模块可进一步核对建议动作的可操作目标，例如当前Make目标、配置选项、依赖搜索路径和生成文件身份。同项目方案复用则可分层评价源码版本或工具链变化后的重新验证需求。联网检索和模型敏感性比较围绕具体信息缺口展开，以完成数、全流程开销和可复现交付评价其增量。

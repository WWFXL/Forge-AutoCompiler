# 简洁构建 Workflow 执行契约

本文对应 `SimpleBuildWorkflow` 与 `scripts/forge_simple_system.py` 的当前科研入口。任务内采用阶段执行与有界恢复，最终结果由独立组件确认；不修改历史实验的运行版本或结果。

## 方案与执行

- 规划 Agent 返回 `SimpleBuildActions`：有序的 `dependency/configure/build` 动作，每步包含命令、`workdir`、前提和依据。末步仍为 `build`。
- 每个命令运行在独立严格 Shell 中。目录由每步 `workdir` 指定，上一命令的 `cd` 不会延续。
- 可选 `build_directory` 是主项目构建目录的规范绝对容器路径，必须位于 `/workspace/repo` 内。它辅助定位观察文件，不改变实际命令或工作目录，不是成功断言。
- CMake 原生输出可以定位实际目录，随后核对 Cache 的源码、目录身份和生成器入口。缺少这行输出时保留目录未知；不手工解析 preset 继承、宏或所有等价 Shell 写法。
- 未绑定目录时不从其他目录找一个旧 Cache 来代替当前证据。成功方案复用和状态路由保留明确的目录上下文。

## 工具与方案错误反馈

规划和恢复工具的参数校验错误保留原始反馈，观察器不因纯文本或非对象JSON中止，也不把错误计为成功证据。方案结构错误提供一次纠正：反馈JSON语法位置或字段错误，要求按当前schema完整重交；无效原响应独立保存，不重复嵌套坏参数。持续无效仍明确失败，不自动修补或执行残缺命令。

## 恢复方案装配

步骤标识中的点号可确定性转换为下划线，同时更新本方案的依赖引用；出现标识冲突仍拒绝，Shell命令和工作目录不变。恢复响应使用当前交接的成功依赖记录，在完整图校验前补回遗漏的成功步骤；JSON正文与结构化工具输出使用相同装配路径。未知引用、前向引用、重复标识及隐式替换成功依赖仍被拒绝，已成功的命令不会因此重新执行。具体工程验证见[libffi装配修复](research/2026-11-16-libffi-recovery-assembly-repair.md)。

## 状态与推进

| 实际情况 | Workflow 动作 |
| --- | --- |
| 命令非零、超时或动作违反约束 | 停止当前执行，交接真实记录和日志；不执行后续动作 |
| 文件新增、原文件内容/权限/链接变化或删除 | 记录后继续执行，结束后单独审查；不据文件变化直接判构建失败 |
| 目录逃出支持范围 | 保留容器与路径隔离约束 |
| 命令成功、配置观察充分 | 保留完成记录，执行下一动作 |
| 命令成功、配置观察未知 | 如实记录 `unknown`，继续已规划且仍在资源限制内的动作；后续实际失败再恢复 |
| 配置阶段末或构建后，已绑定配置与实际文件矛盾 | 交接 `configuration_inconsistent`，不能由 Agent 直接宣告成功 |
| 构建命令成功 | 独立定位主要组件并检查实际编译产物；产物缺失、无效或观察未完成均不能直接标为完成 |

配置阶段可含脚本生成等多个动作，中间动作必须成功，阶段末才要求已知配置没有冲突。Autotools 观察 GNU Make 的标准入口 `GNUmakefile/makefile/Makefile`；自定义入口没有被观察器覆盖时仍可通过真实构建与独立产物证明完成。

`unknown` 不会被改写为 `passed`。这种处理改变的是执行决策，不降低主要组件、精确交付和干净重放的检查要求；源码变化按下述后验审查呈现；`main-build-v1` 不要求完整作者测试，继续单独记录 `not_required`。

## 恢复与观察修订

恢复 Agent 继续读取原源码和权威执行日志，返回完整方案。一次 Agent 任务中，结构错误和恢复方案执行约束错误各至多纠正一次，两类均受原请求、费用和时间预算约束；原始响应、纠正提示和全部请求用量保持计量。服务异常不参与纠正，也不自动重试。

- 真实执行失败需要有依据地修改实际命令或工作目录。仅改说明、步骤别名或观察提示不能触发相同失败命令重跑。
- 只有命令已经成功、交接来自配置观察冲突时，才允许只修正 `build_directory`。新目录必须通过实际配置核验；通过后恢复原成功记录，继续后续动作，不再次运行原命令。
- 无效修订在交付执行器前获得具体反馈。纠正后仍无效则有界停止，保留失败；不以反复更换步骤名称绕开停止规则。
- 动作确实变化时沿用前缀保留与后缀失效机制。依赖或配置动作变化仍触发实际生成物清理。

### 成功依赖与重建配方

原容器的执行进度和新容器的重建配方需要区分：基础镜像已有的工具可以不安装，本轮临时安装的依赖即使当前已可用，也必须留在有效配方中。

- 交接包含 `successful_dependencies` 的步骤、命令ID和实际命令。修订遗漏已成功的 dependency 时，系统默认保留；不将遗漏视为删除。
- 恢复沿用成功依赖的 `step_id`。要废弃或替换，必须在 `discard_dependencies` 中填写原步骤ID及非空理由；未知ID、隐式覆盖和改名重复执行得到明确反馈。
- 保留的成功依赖复用实际命令记录，不因配置后缀变化而在原容器重新安装。显式废弃不证明环境已不需要该依赖，仍以干净重放为准。
- 配方只选择最终有效方案中的成功记录，按实际执行顺序输出；失败命令、过时配置和诊断记录不进入配方。系统不自动合并所有历史成功命令，也不承诺推断任意包管理命令间的语义关系。

## 轻量验证与结果层

评测侧的 `BuildReference.executable_smokes` 可按精确交付文件名提供作者有依据的轻量验证命令，包含来源和非空输出依据。它与完整作者测试分开，不送给规划或恢复 Agent。Workflow 实际执行后，将成功记录绑定到既有 `ExecutableVerificationPolicy`，并加入干净重放的验证脚本；重放还核对交付物及相同 smoke 的命令、工作目录和成功退出码；完整输出哈希继续记录，输出文本差异仅用于诊断。

例如，作者只支持 `fse -V` 时，通过参考数据指定 `/artifacts/fse -V`，无需在 Workflow 编写项目名称分支。显式命令失败、输出依据不符或实际交付的可执行物缺少绑定时，不继续 submit，不记验证通过。`main-build-v1` 缺少显式入口时记录 `missing_native_verification`，不猜版本参数；历史作者测试范围仍使用原默认入口。`main-build-v1` 不要求完整作者测试，记录为 `not_required`。

原容器轻量执行与重放使用相同的30秒子时限。共享库交付依据真实ELF的SONAME补齐精确名称，轻量命令在交付目录的库路径下运行；相同环境进入重放，不依赖原构建目录。退出非零的交付运行可以请求 `delivery_execution_failed` 恢复，Agent修订构建/环境后返回Workflow，仍执行原验证。退出0但输出断言不符属于独立验证定义问题，不允许Agent修改裁判。每个修订分别保存主构建与后检查记录，保留之前失败。

| 结果字段 | 含义 |
| --- | --- |
| `primary_build_completed` | 构建动作与独立主要产物检查是否通过 |
| `delivery` | 是否精确复制交付文件 |
| `executable_smoke` | 实际轻量验证；与完整作者测试分列 |
| `final_verification_passed` | submit 的产物验证与本次实际干净重放是否全部通过；未执行时为 null |
| `clean_replay` | 本次实际 attempt 的状态；前置验证阻断、没有新 attempt 时为 `not_started`，未进入后检查时仍为 `unobserved` |
| `main_build_task_completed` | 原主构建范围的完成，不代表可复现交付完成 |
| `reproducible_delivery_completed` | 主产物、精确交付、最终验证、按 attempt 声明标准的实际重建、源码保持及清理均通过；新标准不代表字节一致 |

`full_completed` 保留旧完整作者测试范围；主构建任务填 null，不能用来冒称完整作者测试通过。旧实验原始标签与证据不改写；E52 继续使用其已发表的分层解释。

## 作者生成文档与恢复上下文

`BuildReference.generated_documents`仅由独立参考声明精确文档路径、原模板、作者依据和预期内容SHA-256；模型动作不能声明生成例外。原文件与模板必须存在且为普通文件。只接受Markdown、RST或TXT文档，拒绝测试目录、源码与脚本；原模板和其余输入继续保护，文档内容或权限偏离声明仍拒绝。`source_protection`将保护输入不变与允许的文档生成分别报告，不将README变化称为所有原文件字节未变。

当前简洁构建入口（初始规划、恢复和强工具Agent）统一使用64,000 Token输入工作预算与32,768 Token输出预留；系统提示、消息和工具/结构化输出定义一并计入。已有`tiktoken`的cl100k_base估算乘1.25并增加2,048 Token协议余量，不宣称为DeepSeek精确分词；实际用量和费用继续按Provider回执计算。输入与输出预留合计96,768，兼容现有单次100,000 Token计量上限，调用前仍按该上限与最高单价保守预留费用。逐请求记录`model.context_budget`；强工具基线不获得规划收敛指令。旧canary入口及冻结证据不改写。先移出可补读的初始内容，再缩短交接日志预览，完整日志及哈希仍保留。若最新AI/Tool组本身过大，整组移入独立原件，使用实际工具结果的首尾片段、请求参数、来源和哈希另起一条证据消息；不拆开工具配对或截断推理字段后冒充原AI消息。没有调用摘要模型。诊断上下文优先保留已核实候选，最多显示六个并记录省略数量，完整查询仍在原始记录中。必要任务与压缩证据仍超限时明确停止，不静默丢弃任务身份。

## 离线恢复指导

`RecoveryHarness`只向`propose_simple`的真实恢复请求追加固定指导；初始规划仍使用原提示和既有`PlanningHarness`。
`run_simple_system(recovery_harness=...)`把指导传到恢复调用，默认不提供时行为不变。
指导绑定共同提示哈希，选择记录包含`scope=recovery`；训练轨迹不注入在线Agent，工具、Workflow和结果要求不由指导修改。
本入口只为后续固定模型的恢复策略比较提供独立变量，不代表新策略已获采用或有效。
高级模型提案须先由用户审核，收到比较指令后才实跑；结果审核之后才写论文。

恢复比较入口`scripts/forge_recovery_harness_comparison.py`对每项目生成一次共同H0初始方案，
随后在两套干净会话分别使用H0/R1恢复。共同规划实际支出一次，各方法部署费用均计入全额规划；
第一处理的修订或结局不进入第二处理。共同规划失败时后两处理未启动，不能填两次恢复失败。
当前18项目任务和实现边界见[准备报告](research/2026-11-09-recovery-harness-comparison-preparation.md)。

## 支持边界

当前目标是 Linux 中 CMake、Make、Autotools 的仓库内主项目构建，动作遵守现有阶段和路径契约。系统不承诺解释任意 Shell 的完整语义，也不承诺任意仓库永不失败。未识别的命令写法可以通过有界执行获取事实；不符合方案接口的输出应在执行前得到反馈。多项目依赖构建交错、仓库外输出和进程重启恢复不由本次修复扩展。

最新实现和针对性实跑见 [共同恢复与验证修复记录](research/2026-11-10-common-recovery-repair.md)与[成功重建验证](research/2026-11-10-clean-rebuild-validation.md)。工程验证不作为模型成功率或 Harness 更新收益。旧运行的严格字节复现标准仍按原协议解释；新运行采用下述成功重建标准。

## 干净重建标准（2026-11-10 起的新运行）

用户已明确同意以同一配方在干净环境中成功重建为要求，不把编译日期造成的字节差异当作构建失败。实际 attempt 记录 `comparison_policy=successful-rebuild-v1`：

- 仍固定同一源码 commit/归档、不可变镜像 ID、资源和成功步骤配方，在空工作区运行构建与验证；执行失败、超时或清理失败仍不通过。
- 交付相对路径集合和产物类型必须一致，每个文件非空、结构有效；可执行物使用相同命令和工作目录复验，必须退出 0。库文件没有适用的版本命令时，轻量运行记为不适用，不冒称运行通过。
- 大小、SHA-256、完整 smoke 输出哈希及相等性继续保存在 `ReplayArtifactComparison`。差异列入 `diagnostic_differences`；`mismatches` 只含阻止成功重建的问题。输出相同、字节相同与重建成功分别表述。
- 原容器的交付清单在 finalize 时仍严格校验大小及 SHA-256，防止接受后交付物变化；源码、脚本快照和镜像身份的完整性检查保持。

这证明的是已声明环境和轻量检查下的成功重建，不证明逐字节可复现或任意输入下功能等价。旧原始结果不重标、不补跑；不同标准的完成率不直接合并。


## 2026-11-11共同修复约定

依赖可在`/workspace/dependencies`内分步骤配置/构建/安装，全部保持dependency角色、先创建目录，主项目阶段仍在仓库。该阶段原文件内容/权限保护为历史策略，现由下述后验审查替代。轻量验证可由独立参考声明有作者依据的正常退出码，系统包装器同时验证退出码与输出并进入重建；未知契约冲突保留未通过、停止无效恢复。主产物通过与后续验证、交付失败分列。完整实现和工程证据见[共同修复报告](research/2026-11-11-common-system-repair.md)，不回写旧实验。

## 2026-11-11成功准备与交付修复

依赖/配置变更触发生成物清理时，先清理，再重新执行有实际仓库生成物的准备及其显式后继；无仓库输出的成功安装可复用，未知记录保守重做。不能在bootstrap成功后删掉configure再跳过bootstrap。仅修改build后缀时仍可保留成功准备记录。成功依赖覆盖冲突一次列全，不允许隐式废弃配方。

相同组件的同名同类型发布/中间变体保留完整观察证据，交付按距仓库根最近、再按路径排序选择一份。作者轻量命令用交付二进制绝对路径；原cwd为`/artifacts`时改到独立运行目录，以宿主UID/GID执行，防止历史/缓存污染交付。新主构建运行前必须补全独立参考的可执行物作者轻量入口，纯库不虚构运行。详见[工程修复及真实构建证据](research/2026-11-11-common-preparation-delivery-repair.md)。旧实验不重标；这些共同修复不计Harness优化收益。

## 初始规划工具约束消融入口

研究入口可显式设置`enforce_planning_tools=True`：初始规划仅执行本次模型请求工具Schema中可用的调用；被拒调用明确反馈、计入预算，不产生新的读取证据。现有读取收敛阈值不变，产品默认关闭。此开关不影响恢复Agent。三组P0旧行为/P0约束/P4约束分别比较工具修正与提示增量，见`cpp-build-planning-tool-p4-comparison-flash-v1`；这项准备不等于模型效果已验证。

## 恢复时的容器依赖查询（2026-11-16）

`run_simple_system`的Forge恢复调用绑定`RecoveryEnvironment`，在原源码/日志读取之外提供两类工具；初始规划和强工具Agent不因此改变。直接调用`propose_simple`时须显式传入与活动交接绑定的`diagnostics`。

- `search_build_files(query, scope)`：固定文本搜索`project/macros/headers/pkgconfig/dependencies`范围，返回路径、行号、片段及不完整标记。系统宏包含版本化aclocal目录；不依赖容器安装ripgrep。
- `inspect_build_environment(kind, query)`：查询常见构建命令版本与实际路径、精确包状态/候选/文件/所属包、包名及描述搜索、精确包描述、文件索引及其就绪状态、aclocal/pkg-config/编译器路径及指定开发环境变量。只读本地数据库；`apt-file`或索引不可用时明确返回`unavailable`，不自动安装或刷新索引。

指导顺序为：用日志里的缺失名称搜索实际文件，核实提供者、安装状态和路径，再决定最小修复。无命中不等于功能被版本移除；证据不足不伪造宏。查询不执行任意模型Shell、不安装依赖、不修改成功阶段；修复仍提交完整方案，由Workflow继续执行。

每次活动交接最多12次查询，另受原任务命令/时间预算约束。查询通过原runtime执行，按`diagnostic`保留命令、退出码、日志和耗时，同步命令frontier；不进入成功配方或重建脚本。搜索最多20条匹配、2000文件、16MB读取和5秒；单文件上限1MB，版本/包查询最多8KB输出、8秒，外层15秒；文件提供者查询内部20秒、外层25秒，均受剩余预算限制。重复查询不因新命令ID被算作新知识。

工程验证入口：`scripts/forge_recovery_environment_repair.py --output <新目录>`。使用脚本回复在真实libffi容器查询并提交预写修复，实际执行交付及干净重建；0 Provider，不能据此声称模型效率提升。细节见[修复报告](research/2026-11-16-recovery-environment-tools.md)。

## 文件变化与后验审查（2026-11-16）

规划/恢复的当前文件策略说明在历史共同提示和Harness指导后独立追加，历史候选摘要绑定保留。当前简洁执行器（Forge、经验Forge及共享该执行器的强工具Agent）使用`posthoc-review-v1`：文件创建、删除、内容、链接或权限变化不再中止Agent/Workflow。正常生成与必要构建适配由Agent在动作理由中说明，仍要求保持核心功能和测试含义。阶段执行保留真实退出码、超时、配置与产物反馈；宿主隔离、严格Shell及受管清理约束继续生效。

`source-baseline.json`保留原文件身份；阶段事件`simple.source_changes_observed`记录原输入变化，终态`source-review.json`完整列出新增/删除/修改及前后摘要。读取不足时标`unobserved`，不伪报未变。新增产物同样进入清单；仅inode/ctime变化不算内容或权限变化。符号链接记录链接本身，不向仓库外展开。完整内容可结合固定原归档、工作目录及命令日志审查。

`source_unchanged`是原文件内容/链接/权限是否未变的事实，不能以构建成功代替；`source_review=pending_review`表示有变化待审，系统不自动推断功能等价。`main_build_task_completed`与`reproducible_delivery_completed`分别依据实际构建及交付/重建结果，不再与文件未变绑定。审查状态单独展示，构建完成不等于功能改动审查通过。无原输入变化的常规生成维持原经验准入；有原输入变化的方案须单独审查批准才能作为已验证经验保存，读取不足不得自动准入。此修复不新增自动语义审查Agent。

干净重建仍从固定原归档和相同镜像执行成功配方，必要构建适配须由配方重现；不把已改目录当作原始源码。旧任务/报告与历史严格检查工具保留原身份，新运行应采用新的默认目标和独立身份，不续用旧授权或改写旧标签。历史CXXCrafter适配器不在本次改动范围，新比较须先统一其后验审查口径。

[libffi零Provider工程验证](research/2026-11-16-source-posthoc-review-repair.md)重现config.guess权限变化、config.sub内容变化后继续完成主库和实际重建，属于工程证据。

### 软件包与文件索引（#772）

`package_search`搜索包名及描述；`package_description`接受精确包名，`package_index(query="apt")`检查Packages/Contents及apt-file。索引缺失与当前索引无匹配分开返回，不自动联网准备。缺失文件可按名称或完整路径查询；同名结果过多时依据实际头文件路径缩小查询。

新查询镜像由`docker/compile/Dockerfile.dependency-index`构建：

```bash
docker build --pull=false --build-arg BASE_IMAGE=autocompiler:gcc13-https-v1 -f docker/compile/Dockerfile.dependency-index -t autocompiler:dependency-index-v1 docker/compile
```

构建前核验本地基础镜像；新任务冻结实际image_id。新镜像装查询工具并保留索引，不预装项目答案。旧默认与冻结实验保持，后续各比较方法统一镜像与准备条件；索引存在不代表始终最新。[真实查询及零Provider恢复](research/2026-11-16-dependency-provider-repair.md)。

## 恢复诊断证据保留（可选研究入口）

新入口 `scripts/forge_libffi_diagnostic_memory.py` 启用 `retain_recovery_diagnostics`。记录只在单个构建任务内共享，初始规划不读取它，不使用个人知识库或旧任务答案。`PlanningContext`在每次恢复模型请求前附加`recovery_diagnostic_memory`，候选不会随旧AI/Tool组被压缩移出；对应快照保存在Agent证据目录。

记录由真实查询反馈生成：最多20条候选及出处、8条近期环境/文件查询和精确候选核实状态，总计最多10000 UTF8字节；省略数量可见，完整结果仍保留于原查询日志。跨恢复交接的环境状态明确可能过期，候选名称本身不证明适用、安装或修复成功。新增提示引导核实描述、文件提供者和安装/路径，不代替Agent作安装决定，不增加工具、查询次数或模型摘要调用。原入口及默认策略保持。

## 下一步依赖诊断证据（可选研究入口）

`run_simple_system(..., diagnose_dependencies=True)`在恢复中启用结构化缺口、任务内候选记录及`diagnose_dependency`组合工具，默认关闭。明确缺依赖日志首次交接先做一次有界只读查询；未知/歧义交给Agent。宏组件命名线索单列为未核实，不把局部无命中解释成版本删除。Agent仍决定修复，工具不安装。

组合工具逐条消费原12查询及任务命令/时间额度；查询与命令frontier/日志一起记录，不进入成功配方。头文件优先常见系统头路径，无匹配再扩大。每次恢复请求附加带来源的缺口、候选与转向提醒；无进展只提醒，新路径不自动撤销全部诊断工具，总预算仍生效。原入口行为保持。实现、验证及边界见[诊断动作改进报告](research/2026-11-16-dependency-diagnosis-selection.md)。

## 规划阶段的依赖检查

`run_simple_system(inspect_planning_dependencies=True)`为方案式Forge启用初始规划环境查询，脚本模型CLI使用`--inspect-planning-dependencies`。历史入口默认不启用；新比较需记录这个配置。直接复用完整方案时跳过模型规划，也不会额外执行这些查询。

规划Agent可从构建说明、CI、CMake/Autotools声明识别主要目标的必要依赖，用`search_build_files`检查项目及已安装开发文件，用`inspect_build_environment`核实工具版本、包状态、包描述、文件提供者与路径。两工具复用恢复阶段的固定查询程序，不接受任意Shell，也不安装包或更新索引。Agent依据证据生成dependency安装步骤，再由Workflow执行配置生成、配置和构建；没有缺口时可直接交付方案，不机械检查所有依赖。

初始查询绑定当前源码和会话，方案生成结束后关闭，最多12次且计入共享任务命令/时间额度。完整命令和日志保留，查询角色为diagnostic，不进入构建重放配方；生成的安装步骤则正常进入可复现构建。规划查询与恢复查询分别记录耗时。恢复仍处理未能预见的真实失败，不承诺消除全部依赖错误。

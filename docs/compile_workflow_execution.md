# 简洁构建 Workflow 执行契约

本文对应 `SimpleBuildWorkflow` 与 `scripts/forge_simple_system.py` 的当前科研入口。任务内采用阶段执行与有界恢复，最终结果由独立组件确认；不修改历史实验的运行版本或结果。

## 方案与执行

- 规划 Agent 返回 `SimpleBuildActions`：有序的 `dependency/configure/build` 动作，每步包含命令、`workdir`、前提和依据。末步仍为 `build`。
- 每个命令运行在独立严格 Shell 中。目录由每步 `workdir` 指定，上一命令的 `cd` 不会延续。
- 可选 `build_directory` 是主项目构建目录的规范绝对容器路径，必须位于 `/workspace/repo` 内。它辅助定位观察文件，不改变实际命令或工作目录，不是成功断言。
- CMake 原生输出可以定位实际目录，随后核对 Cache 的源码、目录身份和生成器入口。缺少这行输出时保留目录未知；不手工解析 preset 继承、宏或所有等价 Shell 写法。
- 未绑定目录时不从其他目录找一个旧 Cache 来代替当前证据。成功方案复用和状态路由保留明确的目录上下文。

## 状态与推进

| 实际情况 | Workflow 动作 |
| --- | --- |
| 命令非零、超时或动作违反约束 | 停止当前执行，交接真实记录和日志；不执行后续动作 |
| 原源码或测试变化、目录逃出支持范围 | 保持错误与保护，不允许通过状态标签放行 |
| 命令成功、配置观察充分 | 保留完成记录，执行下一动作 |
| 命令成功、配置观察未知 | 如实记录 `unknown`，继续已规划且仍在资源限制内的动作；后续实际失败再恢复 |
| 配置阶段末或构建后，已绑定配置与实际文件矛盾 | 交接 `configuration_inconsistent`，不能由 Agent 直接宣告成功 |
| 构建命令成功 | 独立定位主要组件并检查实际编译产物；产物缺失、无效或观察未完成均不能直接标为完成 |

配置阶段可含脚本生成等多个动作，中间动作必须成功，阶段末才要求已知配置没有冲突。Autotools 观察 GNU Make 的标准入口 `GNUmakefile/makefile/Makefile`；自定义入口没有被观察器覆盖时仍可通过真实构建与独立产物证明完成。

`unknown` 不会被改写为 `passed`。这种处理改变的是执行决策，不降低主要组件、源码、精确交付和干净重放的检查要求；`main-build-v1` 不要求完整作者测试，继续单独记录 `not_required`。

## 恢复与观察修订

恢复 Agent 继续读取原源码和权威执行日志，返回完整方案。一次 Agent 任务共享最多一次结构或执行修订纠正；原始响应、纠正提示和全部请求用量保持计量。服务异常不参与这次纠正，也不自动重试。

- 真实执行失败需要有依据地修改实际命令或工作目录。仅改说明、步骤别名或观察提示不能触发相同失败命令重跑。
- 只有命令已经成功、交接来自配置观察冲突时，才允许只修正 `build_directory`。新目录必须通过实际配置核验；通过后恢复原成功记录，继续后续动作，不再次运行原命令。
- 无效修订在交付执行器前获得具体反馈。纠正后仍无效则有界停止，保留失败；不以反复更换步骤名称绕开停止规则。
- 动作确实变化时沿用前缀保留与后缀失效机制。依赖或配置动作变化仍触发实际生成物清理。

### 成功依赖与重建配方

原容器的执行进度和新容器的重建配方需要区分：基础镜像已有的工具可以不安装，本轮临时安装的依赖即使当前已可用，也必须留在有效配方中。

- 交接包含 `successful_dependencies` 的步骤、命令ID和实际命令。修订遗漏已成功的 dependency 时，系统默认保留；不将遗漏视为删除。
- 恢复沿用成功依赖的 `step_id`。要废弃或替换，必须在 `discard_dependencies` 中填写原步骤ID及非空理由；未知ID、隐式覆盖和改名重复执行得到明确反馈。
- 保留的成功依赖复用实际命令记录，不因配置后缀变化而在原容器重新安装。显式废弃不证明环境已不需要该依赖，仍以干净重放为准。
- 配方只选择最终有效方案中的成功记录，按实际执行顺序输出；失败命令、过时配置和诊断记录不进入配方。系统不自动合并所有历史成功命令，也不承诺推断任意包管理命令间的语义关系。

## 轻量验证与结果层

评测侧的 `BuildReference.executable_smokes` 可按精确交付文件名提供作者有依据的轻量验证命令，包含来源和非空输出依据。它与完整作者测试分开，不送给规划或恢复 Agent。Workflow 实际执行后，将成功记录绑定到既有 `ExecutableVerificationPolicy`，并加入干净重放的验证脚本；重放还核对交付物及相同 smoke 的命令、退出码和输出哈希。

例如，作者只支持 `fse -V` 时，通过参考数据指定 `/artifacts/fse -V`，无需在 Workflow 编写项目名称分支。显式命令失败、输出依据不符或实际交付的可执行物缺少绑定时，不继续 submit，不记验证通过。没有显式参考时沿用现有三参数默认检查，不增加盲试参数。`main-build-v1` 仍不要求完整作者测试，记录为 `not_required`。

| 结果字段 | 含义 |
| --- | --- |
| `primary_build_completed` | 构建动作与独立主要产物检查是否通过 |
| `delivery` | 是否精确复制交付文件 |
| `executable_smoke` | 实际轻量验证；与完整作者测试分列 |
| `final_verification_passed` | submit 的产物验证与本次实际干净重放是否全部通过；未执行时为 null |
| `clean_replay` | 本次实际 attempt 的状态；前置验证阻断、没有新 attempt 时为 `not_started`，未进入后检查时仍为 `unobserved` |
| `main_build_task_completed` | 原主构建范围的完成，不代表可复现交付完成 |
| `reproducible_delivery_completed` | 主产物、精确交付、最终验证、实际重放、源码保持及清理均通过 |

`full_completed` 保留旧完整作者测试范围；主构建任务填 null，不能用来冒称完整作者测试通过。旧实验原始标签与证据不改写；E52 继续使用其已发表的分层解释。

## 支持边界

当前目标是 Linux 中 CMake、Make、Autotools 的仓库内主项目构建，动作遵守现有阶段和路径契约。系统不承诺解释任意 Shell 的完整语义，也不承诺任意仓库永不失败。未识别的命令写法可以通过有界执行获取事实；不符合方案接口的输出应在执行前得到反馈。多项目依赖构建交错、仓库外输出和进程重启恢复不由本次修复扩展。

本轮实现和验证见 [共同执行机制修复记录](research/2026-11-09-workflow-state-contract-repair.md)。工程验证不作为模型成功率或 Harness 更新收益。

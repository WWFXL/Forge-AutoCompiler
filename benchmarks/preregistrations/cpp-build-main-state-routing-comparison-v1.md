## 研究问题和两组

相同初始方案与实际观测下，异常时的Jev语义选择能否减少恢复Agent和重复探索，同时保持主要程序/库构建成功？规则组与Jev组共享当前方案、作者文件、容器环境、候选动作和恢复Flash；经验注入关闭。正常且观测明确的路径不调用Jev。

Jev输入为阶段/目的、实际命令/退出、关键日志、配置观察、主产物观察状态及候选说明。一次请求含state/action两个Choice。状态类别为完成、前置缺失、执行失败、证据不足；动作只能选择本状态生成的候选或Agent。语义输出不能覆盖非零退出、缺少有效产物等反证，不能生成Shell或修改目标。

## 候选与恢复

1. configure失败、根CMake声明最低版本时可提出普通pip安装满足作者最低版本的CMake，并在现有配置/构建中使用新工具。是否适合当前失败由规则或Jev选择；作者版本声明本身不等于当前失败原因。
2. build失败且配置观察缺失/失败、当前已有配置方案时，可清理新生成物并重建已有配置后缀。
3. 主产物观察未完成时可再观察；只有实际检查通过才能继续。
4. 无适用候选或选择Agent时，沿用恢复Agent返回修订方案的路径。每槽最多两个不同局部动作，同一动作不自动重试；真实局部动作失败及随后恢复全部计费并保留。

新任务版本main-build-v1：执行成功构建动作，主要程序/库有效、来自当前源码且原源码/测试保持。主要构建成功单独记录；main_build_task_completed还要求源码终态检查与实际cleanup通过。完整作者测试不要求，明确记not_required而非通过，旧full_completed留空。

精确交付、干净构建重放、耗时与资源清理独立报告。重放失败不能隐去，但也不能把重放指标与主要构建成功混为一谈。新旧任务终点不同，不把旧测试失败重新标为通过或直接做跨批成功率差值。
